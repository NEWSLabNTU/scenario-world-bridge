# 046: Stacked NDT aligns fail the ego's reset on a loaded host, and queue more aligns

**Severity**: high (on a loaded host, Tutorial 1 ends `error` before the ego drives:
"Simulator waited for the Autoware state to transition to WAITING_FOR_ROUTE, but time is up.
The current Autoware state is INITIALIZING"). **Status**: open; the fix lands after the 080
landing, on its own branch (the rename stays free of behaviour changes). **Found**:
2026-11-18, swb 241, the 080 exit runs of Tutorial 1. Investigation:
`~/nas/home/2026-11-18 080 T1 NDT investigation (241)/REPORT.md`.

## What happens

Three runs of `drive_to_goal.xosc` on CARLA Town01 ended `error`, all in INITIALIZING:

- 2026-11-17T22-03-45 and 22-08-48, at fbc9cf5, with load5 about 120-140 on 24 cores;
- 2026-11-18T03-33-05, at b163816, with load5 about 44.

The last pass was 2026-11-17T15-01-48, at fdf0908. Every NDT align in every one of these runs
returned "align server succeeded", with no unstable-pose or large-error warning. What changed
was how long the aligns took, from pose_initializer's log ("Call align server." to "align
server succeeded"):

| run | aligns (s) |
|---|---|
| pass, 15:01 | 11.4, 23.4, then 5-10 per later reset |
| 22:03 | 126.5, 169.1 |
| 03:33 | 72.4, 47.2, 10.3, 27.8 |

## Why: two initializers, two 60 s budgets, and calls that stay queued

1. **Two initializers.** Autoware's `automatic_pose_initializer` runs whenever `gnss_enabled`
   is true, which is the default of `tier4_localization_launch`'s
   `pose_twist_estimator.launch.xml`. At the ego's start it asks pose_initializer to
   initialize from the GNSS pose. At 03:33 its first try failed ("The GNSS pose has not
   arrived", 03:35:12), and its retry started an align at 03:35:22, before the scenario's
   reset reached the agent (1794944123.7).
2. **The agent's initialize queues behind it.** The vehicle agent calls
   `/api/localization/initialize` with the scenario's pose. pose_initializer serves one align
   at a time, so the call waits for the GNSS align to finish, then runs its own.
3. **Two 60 s budgets.**
   - The agent allows 60 s per initialize call: `INITIALIZE_TIMEOUT = 60.0`,
     `src/scensim_agent/scensim_agent/adapters/autoware_ros.py:84`. It retries up to
     `initialize_attempts` times (`adapters/autoware.py:476-489`).
   - The relay allows 60 s for the whole reset: `RESET_TIMEOUT = 60.0`,
     `src/scenario_agent_relay/scenario_agent_relay/episodes.py:23`.

   At the pass the reset took 34.0 s (`reset ego-1-1794899035 -> OK in 34.0 s`). At 03:33 it
   failed: `reset ego-1-1794944123 -> FAILED in 60.0 s: agent did not reply to reset within
   60.0 s`. At 22:03 the agent gave up: `localization initialize refused 5 times:
   /api/localization/initialize: no response in 60.0 s`.
4. **A timed-out call is not cancelled.** The service request stays in pose_initializer's
   queue and aligns later; the agent's next attempt queues another. This is the "Call align
   server / align server succeeded" loop in the logs. At 22:xx the aligns went on until
   22:15, after both runs had ended. Each queued align is a 200-particle NDT search on 12 CPU
   threads (cuda_ndt_matcher is not built on 241), so the timeouts themselves add load.

The rename (080) changes nothing on this path. The investigation diffed fdf0908..b163816 with
the old names mapped to the new: the pilot and ego launches, the agent's Autoware adapters, the
relay's episodes and the profile's localization arguments are all unchanged apart from text.
Load is the leading explanation (CARLA's tick p50 was 4.8 ms at the pass, 31-61 ms at the
failures), but the pass recorded no load, so this is not proven. The exit runs log loadavg
every 5 s and the align durations from now on.

## Design of the fix (ranked)

a. **Do not re-send while an align is in flight.** After an initialize call times out, the
   agent waits on `/api/localization/initialization_state` (INITIALIZING, then INITIALIZED or
   UNINITIALIZED) instead of making a fresh call. It calls again only once the state says the
   earlier align has ended and did not take the scenario's pose. This ends the queue growth
   whatever the budgets are.
b. **A managed ego turns `automatic_pose_initializer` off.** The agent always initializes
   explicitly, at the scenario's pose, so a GNSS initialization only competes with it. The
   profile does not expose this today: `autoware_sim_profile`'s
   `tier4_localization_component.launch.xml` (generated by
   `scripts/sync_localization_component.sh`) does not pass `gnss_enabled`, so it takes
   `pose_twist_estimator.launch.xml`'s default, true. The fix adds a `gnss_enabled` argument to
   the generated component and the profile, set false for a managed ego. It must be checked
   that a value set at the include reaches `pose_twist_estimator.launch.xml` through
   `localization.launch.xml`, which does not declare it. With `gnss_enabled` false,
   pose_initializer also stops using GNSS for an initialize without a pose; the agent always
   gives one.
c. **The budgets become parameters**: the agent's per-call timeout and the relay's reset
   timeout, with today's 60 s as the default and the reason in the parameter's description.
