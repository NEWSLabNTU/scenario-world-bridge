# Phase 083: CARLA 1.0

CARLA 1.0 (released 2026-11-17, Unreal Engine 5.8) becomes a supported simulator next to
0.9.16: the CARLA world server and acb build for it, the T3 suites that run on CARLA pass
on it, and a release ships both. CARLA declares the UE 4.26 line (0.9.16 and earlier)
obsolete and to be deprecated, so 1.0 is where CARLA support goes next.

**Status**: started 2026-11-18, while 082's 0.1.0 release builds (user: "start CARLA 1.0
port"). Steps 2 (probe, 139) and the native ROS 2 study (241) run first.

**Source**: user, 2026-11-17: "CARLA 1.0 release is out. Explore it and plan the support."
Read the same day: the GitHub release `1.0` (carla-simulator/carla, published
2026-11-17T10:01Z) and its changelog. Nothing was installed or run yet.

## CARLA's own scenario and Autoware stack, and where it overlaps ours

Read 2026-11-17 (the CARLA 1.0 changelog, `Docs/autoware.md` on `ue58-dev`, ScenarioRunner's
`v1.0` release of 2026-11-06). CARLA itself does not load scenario files: the scenario
layer is its client tools.

| CARLA 1.0 | What it is | Ours | Overlap |
|---|---|---|---|
| **ScenarioRunner 1.0** (`ue58-dev`, needs CARLA 1.0, py_trees 2.6) | Python client: its own Python scenarios, route scenarios, OpenSCENARIO 1.0 with "initial support" for actions, conditions and the storyboard (a per-attribute table), OpenSCENARIO 2.0 optional; pass/fail by criteria it adds, since OpenSCENARIO 1.0 defines none | SSv2 (the scenario engine, OpenSCENARIO 1.x and TIER IV's YAML, its own evaluation), behind the world protocol, on CARLA and Isaac | **Same job, different engine.** Both run `.xosc` on CARLA. SSv2's coverage, its Autoware semantics (the AD API, managed ego) and simulator independence are why we use it; ScenarioRunner is CARLA-only. |
| **Leaderboard** (and its agent API) | Route-based evaluation of a sensor agent, infraction scoring | Suites, judges, `result.json`, pilots of six kinds | Scoring overlaps: Leaderboard's infractions are judges we could offer. |
| **Scenic mode** (NuRec hybrid example) | Probabilistic scenarios on recorded scenes | none | None today. |
| **Autoware integration** (`PythonAPI/examples/av_stacks/autoware/`, not in the release package) | "no bridge process": the server publishes sensors and vehicle status on ROS 2 itself and applies Autoware's commands; `classical` (full stack, NDT, lidar perception) or `e2e` (VAD, six cameras); an installer that builds Autoware from source; a launcher (`run_carla_autoware.sh`); map tools; Humble or Jazzy; needs CARLA built with `-DENABLE_ROS2=ON` | acb (a client-side vehicle bridge, sensors published by the bridge), the car's Autoware packages from one spec, spec physics checked after every spawn, `carla-town-autoware-maps` (lanelet2 and point clouds for the towns), the overlay and TensorRT notes | **Direct overlap on the vehicle side.** Theirs needs a ROS-enabled CARLA build (the package is not one) and one ego; ours runs on the packaged server, several pilots, any simulator behind the protocol, our car spec. Their map tools (stop signs, traffic-light lane links) may improve our town maps. |
| **Native ROS 2 sensors** (FastDDS, CycloneDDS or Zenoh; Ackermann control) | sensors published from inside the server | acb publishes sensors from a client | A possible faster sensor path, measured before adopted (non-goal until then). |

**Revisited 2026-11-18** (user): "We revisit the CARLA to autopilot connection because
CARLA now supports ROS natively. See how Autoware 1.5.0 and modern 2.1.0 can work with it."
So decision 4 above is no longer a later measurement but the first question: what CARLA
1.0's native ROS 2 connector publishes and accepts, against what Autoware 1.5.0 (acb's
topics today) and Autoware 2.1.0 expect, and whether acb stays, thins to an adapter over
the connector, or goes. Both Autoware releases are installed on host 133 for the trial.
The non-goal on the native connector below holds only until that study reports.

**Study result** (241, 2026-11-18, CARLA `ue58-dev` 94f2985, source only; report
`~/nas/home/2026-11-18 083 native ROS study (241)/`): keep acb whole and port it
(carla-rust `carla-10`). The native connector does not carry what we rely on:

- Its Autoware control is kinematic (it integrates the commanded acceleration and overwrites
  the body's forward speed): the spec's engine, brakes, pedal maps and lags are bypassed;
  steering goes through an MKZ table; no command timeout; gear, lights, emergency and
  engage are ignored.
- One ROS domain per server and absolute Autoware topic names: one Autoware ego per server.
- Its clock is episode seconds from 0 with no offset and goes back at a world load (our
  `BASE_NS` rule).
- Status and sensors: commanded, not measured, steering; lidar intensity 0 or 1 and rings
  from point counts; no per-point time; a yaw-only IMU; ground-truth GNSS.

Later, optional: native sensors if the probe shows the client stream is the bottleneck
(needs a clock offset and a better lidar first); a single-ego "carla-native" pilot for stock
CARLA; CARLA's map tools to regenerate the `_Opt` towns' lanelet2 and point clouds.

Autoware 2.1.0: the vehicle interface is wire-compatible with 1.5.0, but
`tier4_ad_api_adaptor` is gone: of the external API scensim's Autoware agent uses, only
engage and the velocity limit survive. Nothing serves the AD API's cooperation endpoints
either, so the agent uses the planning modules' own `rtc_interface` when the adaptor is
absent (branch `2.1-agent-adapi`; `docs/design/user-workflow.md`); the overlay forks rebase onto 2.1.0's packages and the TensorRT version is checked
again.

## Goal

On a host with CARLA 1.0 (the packaged release plus the AdditionalMaps pack):
`carla_version: "1.0"` (or detection from the server) selects the 1.0 binaries; tutorial 1
and the CARLA T3 suites pass on 1.0 with their 0.9.16 verdicts, or with each difference
explained and recorded; 0.9.16 keeps passing unchanged.

## Steps

1. **Docs** (this doc).
2. **Probe** (one host, no code): install the package and the pack, measure the RPC start,
   VRAM and tick time on `Town01_Opt` at Epic and Low with the ego's sensor set from the
   Python client; check the town list, `get_server_version()`, and that our Town01 lanelet2
   map lines up with `Town01_Opt` (a few waypoints compared).
3. **carla-rust `carla-10`** (the user's crate): the feature, LibCarla 1.0 built or
   prebuilt, the API differences (renamed methods, the rotation types, the actor and
   telemetry calls); released on crates.io before the pins move here. Its issues go to
   carla-rust, the user's call where.
4. **The CARLA world server and acb for 1.0**: a binary per CARLA version behind 070 A's
   launcher (as 082's tarball already plans for several versions); the town-name mapping;
   the rotation-order audit of the coordinate conversion, with a test from a known pose.
5. **Vehicle physics on Chaos**: the spec's mapping to Chaos's vehicle parameters, acb's
   verification and drift check, the steering and braking measured against 0.9.16's
   reference runs (the vehicle check, `just vehicle-check`).
6. **Suites on 1.0**: the CARLA T3 suites at 1.0, compared with the 0.9.16 references; each
   verdict difference classified (physics, rendering for camera pilots, map geometry, the
   new collision determinism). **Done 2026-11-19** (swb 243, host 243): see "Step 6: T3 on
   CARLA 1.0" below.
7. **Release**: 1.0 in 082's tarball matrix and support tiers ("Tested" once step 6 passes;
   0.9.16 stays "Tested" until the user drops it); the docs' "tested with" table. **Open.**

## Exit criteria

- Tutorial 1 and the CARLA T3 suites pass on CARLA 1.0, differences from 0.9.16 recorded.
- 0.9.16's T3 suites unchanged.
- A 1.0 server with a 0.9.16 binary (or the reverse) is refused by name, as today.

## Non-goals

- CARLA's native ROS 2 connector as our sensor path (the bridges stay clients), until a
  measurement says otherwise.
- NuRec, Cosmos, DLSS and the ray-traced lens cameras (rendering features; a later phase if
  a study needs them).
- Dropping 0.9.16 (the user's decision, when CARLA deprecates the UE 4.26 line).

## Open

- Whether the 0.10 work (`carla-0100` in carla-rust) is kept or dropped once 1.0 builds.
- Whether our Autoware maps for the classic towns still match their `_Opt` versions, or
  must be regenerated (CARLA's new map generator is one way).
